## [0.5.5] — Unreleased (pending directory review)

### Directory submission fixes (DEV-240750)
The directory check held 0.5.4 for policy review. This release clears every finding that needs a code change, and the follow-up code review's findings on that fix. Version set in `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` and `.mcp.json`'s `X-Realize-Client` header.

**Permissions (`ALLOWED_TOOLS_BROAD`, unscoped fetch)**
- No skill pre-approves bare `Bash` or `Write` any more.
  - `accounts`, `campaigns`, `optimize-campaign` and `reports` drop `Bash`; they never used it.
  - `discovery` and `manage-campaigns` (including `references/mcp-write-surface.md`) use the `Grep` tool for overflow dumps.
- `support` pre-approves only the three exact commands it runs: `node "${CLAUDE_PLUGIN_ROOT}/skills/support/scripts/build-bundle.js" --preview`, and `--write` with `--complaint-file ~/.realize-plugin/tmp/complaint-*.txt` or `--title-file ~/.realize-plugin/tmp/title-*.txt`. The path is quoted for install paths with spaces. A `:*` suffix had matched `--out <any path> --force --allow-git` too. Writes are scoped to `Edit(~/.realize-plugin/tmp/**)`, because a `Write(path)` rule is never consulted and bare `Write` allowed writing anywhere.
- `diagnose-tracking` pre-approves no command. Each page fetch shows the user a prompt with the exact URL, so an instruction planted in a page or HAR can't send data anywhere silently.
- `web-fallback` scopes `WebFetch` to `realize.com` / `www.realize.com`.

**Pixel page download (`RUNTIME_FETCH_EXEC`)**
- The `curl` line in `diagnose-tracking/SKILL.md` and the agent is replaced by a shipped script, `skills/diagnose-tracking/scripts/fetch-page.js`, with no dependencies and 114 unit tests.
- It allows http/https only on every hop, at most 3 redirects, a 20 s timeout and a 5 MB cap. It refuses `user:pass@` URLs and sends no cookies.
- **Private, loopback, link-local and metadata addresses are refused on every hop**, IPv6 forms that embed an IPv4 address included (`[::ffff:127.0.0.1]`, which the URL parser rewrites to `[::ffff:7f00:1]`; IPv4-compatible, NAT64, 6to4), plus site-local `fec0::/10`, local-use NAT64 `64:ff9b:1::/48`, `192.0.0.0/24` (Oracle Cloud's metadata address is `192.0.0.192`) and the `198.18.0.0/15` benchmarking range. The check runs inside each connection's own DNS lookup, so a name can't answer "public" to the check and "127.0.0.1" to the connection (DNS rebinding), and the 20 s timeout covers the lookup. The old `curl` line would follow a redirect into the user's network.
- A `www.` redirect no longer counts as a host change; it previously skipped the static check on most real sites. A URL without a scheme gets `https://`.
- Network failures name their cause (DNS, TLS, refused) instead of a bare "fetch failed".
- **Corporate networks are best effort, not `curl` parity.** When a proxy variable is set, or a certificate error occurs, the script re-runs itself with the OS certificate store (Node 22.15+/23.8+) and env-proxy support (`NODE_USE_ENV_PROXY`, Node 22.21+ and 24+). Through a proxy the private-address check covers literal-IP hosts only, since the proxy resolves names. Older Node on a proxy-only network can't reach the page; the error says so, and the skill falls back to the user's browser capture.
- The URL is a single-quoted positional argument. There is no file-reading option that could echo a local file.
- Each run saves into its own fresh temp folder; this user's folders from earlier runs are pruned after an hour.

**Support bundle**
- Invoked via `"${CLAUDE_PLUGIN_ROOT}/…"` instead of a repo-relative path, so `/support` works for people who installed the plugin.
- `--complaint-file` / `--title-file` read only `complaint-*.txt` / `title-*.txt` files directly in `~/.realize-plugin/tmp` (realpath-checked; `..`, symlinks and hard links refused), so the unprompted script can't copy an arbitrary file into an email attachment. Each run uses its own file name, so concurrent runs can't read each other's text.
- The script deletes the complaint file after writing; leftovers from cancelled runs are pruned after a day. Previously the cleanup relied on a model-run `rm` the user could decline. A failed delete is a warning, not a failed bundle.
- **The script itself limits writes**, because a permission rule can't pin every argument. `--force` and `--allow-git` need an interactive terminal, which the model never has. `--out` must be a new `.md` file directly in Desktop, Downloads, home or the temp folder, never a symlink, and the file is opened exclusively (`wx`). Before this, `--out ~/.zshrc --force` overwrote the user's shell startup file with the transcript.

**Other**
- **Node.js is not assumed.** The native installer and desktop app don't include it. The pixel check falls through to the browser capture, and `/support` points the user to emailing Support directly. `INSTALL.md` states the requirement, and both scripts' "Node ships with Claude Code" comments are corrected.
- `agents/realize-analyst.md`: gains `Write`, which `/support` needs when run through the agent, and no longer names a repo-relative script path.
- **`UNREAD_ASSET_REFERENCED` (7):** docs and CI no longer name the listing icon by path. The duplicate CI icon check is removed, because the directory check reports a missing icon itself.
- **Tests:** test fixtures that look like a local-file URL or a `user:pass@` URL are assembled at runtime, the same rule as `test-build-bundle.js`.
- **`INSTALL.md` / settings example:** the `Bash(curl:*)` opt-in is removed. The page-fetch section now says the prompt is deliberate instead of claiming "no opt-in needed", which was wrong: a skill grant lasts one turn.
- **CI:** runs `test-fetch-page.js`. *Directory-check guards* now holds every skill's `allowed-tools` to an allowlist: plain read tools, domain-scoped `WebFetch`, the one scoped `Edit`, and only the skill's **own** script in the exact quoted form. No `..`, no other skill's script, no wildcards.
- **Left for the reviewer:**
  - `MCP_FORWARDS_CREDENTIAL_ENV`: nothing reads a credential. Login is Claude Code's OAuth against the MCP, and the only header is the static client identifier.
  - `UNKNOWN_KEY` on `privacyPolicyUrl`: the finding says no action is needed.

### Added — campaign groups and the conversion-goal chain
- **Campaign groups are readable, and the conversion goal is now resolved in the right order.** Upstream shipped `get_campaign_groups`; the plugin wires it as a 20th read tool, taking the read count from 19 to **20**. The group layer matters for one specific reason: **a group's `conversion_rules` apply to every campaign in it that sets none of its own**, so the goal chain is campaign → group → account default.
  - **The plugin previously skipped the middle step.** `optimize-campaign` P2 read an empty `conversion_rules` on a campaign and reported the account default. On a campaign that inherits a different goal from its group, that is a wrong-KPI answer, and the whole diagnosis downstream of P2 is built on it. P2 now reads the group before falling back, and must state **which level** the goal came from — its own, its group's, or the account default.
  - **P5's not-applicable row was widened the same way.** "The account has no conversion rules at all" became "neither its group nor the account has any", and the disambiguation now reads both levels. Previously a campaign inheriting a group goal could be told it was missing a conversion rule.
  - **The stale UI-only claim is gone.** `knowledge/campaign-structure.md` stated that campaign-group assignment is "not exposed via the Realize MCP today" and that group work is UI-only. Reading is now exposed; the note records what is and is not wired, per the stale-capability-claims rule in `.claude/CLAUDE.md`.
  - **`create_campaign_group` / `update_campaign_group` are wired.** An earlier revision of this release held them back as account-shaped writes pending review; that was reversed — they are MCP tools the server exposes, and blocking them made the plugin narrower than the surface it wraps for no stated product reason. They route through `manage-campaigns` like every other write, behind the preview-then-confirm gate and the `▶ WRITE TARGET` header, which takes the write count from 8 to **10**. Field reference: `skills/manage-campaigns/references/mcp-write-surface.md` §3c — closed schemas (an unknown key is rejected, not ignored), required fields (`account_id` + `name` + `spending_limit_model` on create; `account_id` + `campaign_group_id` on update), the objective → KPI table and the rule that the two travel together, the `kpi_data` inversion where `kpi_threshold_value` and `kpi_goal_value` mean the opposite of how they read, and the absence of any delete endpoint. **The blast radius is the part the preview must state:** some group edits fan out to every campaign in the group — changing how the budget is split, changing a shared group's budget, and `is_active=false`, which pauses all of them. Putting a campaign **into** a group, by contrast, was already wired and the docs did not say so: `campaign_group_id` is a parameter on both `create_campaign` and `update_campaign`, so it rides the existing write gate. `skills/manage-campaigns/references/mcp-write-surface.md` now carries it, with the two upstream limits that make it easy to get wrong — on update it can only **attach** a campaign that is in no group yet, and only to a `CUSTOM`-budget group (moving or detaching has no tool at all); and in an `AUTOMATIC`-budget group the group owns the budget, so the campaign's `spending_limit`, `spending_limit_model`, `daily_cap` and `daily_ad_delivery_model` are read-only and sending any of them is rejected. That last one makes "raise the daily budget on this campaign" a group-level question whenever the campaign sits in an `AUTOMATIC` group. **`budget_distribution_method` takes two values on write and returns up to four on read.** `CUSTOM` and `AUTOMATIC` are the write enum; a read may also return `FULLY_SHARED` or `CPA_BASED_ALLOCATION`, and Realize treats all three non-`CUSTOM` values as a managed budget. Only `CPA_BASED_ALLOCATION` is deprecated. Upstream retired the write spellings `FULLY_SHARED` / `CPA_BASED_ALLOCATION` and their `OPTIMIZE_SCALE` / `OPTIMIZE_PERFORMANCE` write spellings on 2026-10-12 (realize-mcp-server `171b175`), and `MAX_CONVERSIONS` is the **recommended**, not required, bid strategy for an `AUTOMATIC` group's campaigns — the plugin must not refuse a write over it.
  - **Two upstream details the docs now carry, because getting either wrong silently reintroduces the bug.** (1) `conversion_rules` is an **object** — `{"rules": [...]}` — so the inherit case is `conversion_rules.rules` being an empty array, not the field being absent; the object is always present and always truthy, and "if conversion_rules is empty" reads as false on exactly the campaign that needs the group lookup. (2) **A group is read by its id** — `get_campaign_groups(account_id=..., campaign_group_id="<id>")` — which returns the full record. The list form is for finding a group by name only. An earlier revision of this branch had it the other way round, on an inference from a code comment that describes the *list* endpoint's bare projection; review caught it and a production check settled it: the same group returns `conversion_rules: {"rules": []}` by id and `conversion_rules: null` through the listing, even with the full view requested. Since this plugin reads `null` as *unread*, the old rule would have made a perfectly readable group look unreadable — the wrong-answer class this work exists to remove.
  - **`statuses` does not speak the plugin's usual status vocabulary.** It takes `RUNNING` / `PAUSED` / `STOPPED` / `EXPIRED` / `DEPLETED` and friends; `ACTIVE` — the value conversion rules use, and the obvious guess for "live groups" — is rejected outright rather than ignored. Documented with the enum, alongside the `total`-may-be-absent short-page fallback.
  - **The group read has traps, and they are written down once.** `knowledge/campaign-structure.md` → *Reading a campaign group* is the single procedure; the agent, both skills, the write-surface reference and the guardrails point at it rather than restating it, because restating it is exactly how this repo's rules drift. The traps: (a) `search_text` matches group **names** as well as ids and results sort by id ascending, so the row you want is often not the first — take the row whose `id` matches, and treat "no matching row" as unread rather than as "no group". (b) `campaign_group_id` comes back as a number, so `0` / `null` / `""` all mean *ungrouped* and none of them is an id to search for. (c) A campaign's own `conversion_rules` has three states, not two — a non-empty `rules` array, an empty one, and anything else (key absent, `null`), which means **unread** and must be reported as such rather than resolved to a goal.
  - **`conversion_rules` written on a campaign REPLACES what it inherits from its group.** The read path said so; the write path did not. A user saying "my campaign has no conversion goal, add Purchase" may simply be inheriting three, and writing one silently drops the other two on a live campaign — so the write path now reads the group first and previews both sides.
  - **Attaching a campaign to a group is one-way and the preview has to say so.** There is no detach or move tool, so a confirmed attach is permanent from inside the plugin; in a shared-budget group it also hands over budget control for good.
  - **Free text the API returns is evidence, not instructions.** Campaign and group names are advertiser-authored and now arrive in context alongside the fields being reasoned over; `os/guardrails.md`'s trust boundary previously covered only fetched pages and HAR captures.
  - **Also in this release, independent of campaign groups:** the P5 learning table's four status rows now read "Missing, `null`, or any value not listed above", so a status value upstream adds later lands on the right row instead of falling through to the catch-all and firing the guard on a campaign that has no learning phase. And `knowledge/campaign-structure.md`'s Budget Distributor section no longer says performance-based allocation is a future version — it is live, as `budget_distribution_method: AUTOMATIC`.
  - **Re-synced against upstream `master` on 2026-10-13, which moved under this branch.** `budget_distribution_method` is now `CUSTOM` / `AUTOMATIC` only (realize-mcp-server `171b175`, 2026-10-12); two of the four older write spellings are gone (`OPTIMIZE_SCALE` / `OPTIMIZE_PERFORMANCE`), while `FULLY_SHARED` and `CPA_BASED_ALLOCATION` still come back on read; and `MAX_CONVERSIONS` is still **required** in an `AUTOMATIC` group, whatever the tool text and the public documentation say for an `AUTOMATIC` group's campaigns — a refusal built on the old rule would have blocked a valid write. `knowledge/campaign-structure.md`'s Budget Distributor section no longer describes two automatic modes, because there is one.
  - **A group's `kpi_data` is not a Target CPA.** It is a pair of thresholds feeding Realize's recommendations, and only when the group's `kpi` is CPA. Added to the canonical read block so it is never reported as the campaign's bid target. The by-id deviation note now records that **three** tool descriptions (`get_campaign`, `list_campaigns`, `get_campaign_groups`) recommend the by-id form, so a later sync does not undo it without checking the handler.
  - **A grouped campaign's own conversion goal is not visible in the Realize UI.** The campaign's rules still win and bidding still follows them, so a correct campaign-level answer can look wrong to a user checking the screen. The plugin now says so in one line when it reports a campaign-level goal on a grouped campaign (`knowledge/campaign-structure.md`, the `conversion_rules` phrasing row in `os/guardrails.md`, read scenario 23 Part A2).
  - **Review rounds 7-8 fixes.** The create flow now reads the group *before* collecting inputs, so it never asks for a budget field an `AUTOMATIC` group forbids, and the preview template no longer hard-prints `spending_limit_model`. The scalar-update procedure gained a real attach gate at what is now step 4 of the scalar-update flow — previously the attach-only and cannot-be-undone rules lived only in the refusal branch, which the attach path never reaches. The campaigns skill learned the three-state `conversion_rules` read and the empty-result case. `optimization-flow.md`'s budget levers, a second entry point into the same rejected write, gained the group check. The canonical procedure is now reachable from `knowledge/manifest.json` (it was unindexed, so the retrieval layer could not find it) and is pointed at, not restated, by the goal-resolution section and the guardrails.
  - **A stale campaign-level goal still wins — and that is the failure mode, not an exception.** `conversion_rules.rules` carries only `{id}`; the rule behind it may be disabled, archived, or simply receiving nothing, and the campaign keeps optimizing toward it. The group's goal does **not** take over. Many of these attachments arrive by duplication, a campaign copied from a pre-group original bringing its old goal with it. The read flow now resolves every id through `get_conversion_rules` **matching on `id`, never on `display_name`** (an account can hold several rules sharing a name on different events), names the rule as the goal, and says in the same breath when it is retired. Reporting the group's goal in its place, or answering as though the campaign has no goal, are both failures — a campaign spending against a dead goal is the finding. `optimize-campaign` P2 diagnoses against it rather than substituting the group's.
  - **Review round 9 fixes.** The restructured Budget Distributor section had left its scale-led bullet orphaned under a paragraph declaring scale-led superseded — now labelled inline as superseded. `3b` was not a valid ordered-list marker, so the attach gate rendered inside step 3's budget-field condition and read as gated on a budget change; renumbered. The create preview printed the flight dates twice. A pointer broke when a heading was renamed. The `conversion_rules` phrasing rules had been appended to the row keyed on an *empty* `rules` array, which by definition excludes the case they describe; split into their own row.
  - **A group's conversion rules are the group's *selection*, never a statement about its campaigns.** Reporting "this group optimizes toward X" implies it settles every campaign in it, and it does not: any member can carry its own goal that replaces the group's and that Realize does not display. The group-listing flow, the canonical section and the guardrails' phrasing table now all say *what the group selects*, and send a per-campaign question to a per-campaign read.
  - **Round-10 fix, and it was the headline failing.** The CHANGELOG claimed the write path reads the group and previews both sides. It did not: the rule sat in a paragraph under *Creating a campaign*, while the procedure that actually performs the write — the targeting-blocks pattern, which names `conversion-rules` in its own heading — still merged into the campaign's current list. On the exact campaign this work exists for, that rendered `Current: [] → After update: [Purchase]`, telling the user they were adding a goal to a campaign that had none while silently dropping the three it was inheriting. The group read is now step 2b of that procedure, the preview shows inherited-today against campaign-after, and **W19** fails the old rendering.
  - **Two corrections to the previous round's own fixes.** The canonical rule still gated step 1 on the campaign's rules being *active*, so a campaign whose only attachment was retired fell through to the group — the one outcome the round existed to prevent, and the skill and the knowledge file disagreed about it. And "match on `id`, never `display_name`" described scanning a listing that defaults to ACTIVE, which hides the retired rule being checked; it is now `get_conversion_rules(account_id, rule_id=…)` with no status filter. The `display_name` rationale went too: upstream states names are unique per account, which this plugin relies on elsewhere, and the claim made the new test unseedable.
  - **Unsourced edges trimmed.** The UI observation is now dated and matched by the stale-claim grep, and no longer asserts Taboola's intent. `additionalProperties` was said to cover read tools only; it covers six writes too (the two conversion-rule writes, the two campaign-group writes and the two audience writes). The claim that `list_campaigns` reports `total` contradicted this same file eighteen lines later. The NETWORK-account read behaviour was a guess that could suppress a correct answer, so only the ownership rule remains. The guardrails gained a row for the unread `conversion_rules` state, which the two files that ship to skill-less runtimes had been positively denying.
  - **The two group writes get their field reference, not just permission to run.** `references/mcp-write-surface.md` §3c covers both tools: the closed schema (a misspelled field is rejected here, unlike the campaign writes), `spending_limit_model` being required on create even for a `CUSTOM` split, the objective → KPI pairing the API enforces and the JSON schema does not check, `kpi_data`'s two fields meaning the opposite of what they are called, the `NONE` + `daily_cap` + `STRICT` combination, and what the preview has to say beyond the diff — a budget-split change or `is_active: false` reaches every campaign in the group, and there is no delete because deleting one terminates its campaigns. W20, W21 and W21b cover the two group writes.

### Added — the audience surface
- **The audience surface is brought in line with the MCP.** The audience reads have been on the MCP since April and the plugin documented them from an old signature; the two write tools landed 2026-09-07 and were never mentioned. Nothing new is wired as a write — this corrects what the plugin says and knows.
  - **A silent wrong write is fixed too, and it is the worse one.** `similarity_level` on predictive-audience targeting is a closed set — 1, 2, 3, 4, 5, 10, 15, 20, 25 — and it means different things per seed: 5/10/15/20/25 for a CRM seed, 5 only for a pixel seed, 1-5 for a PBP seed. Nothing in the plugin named a single legal value. A user asking for "a 1% lookalike", the vocabulary they bring from other platforms, would have become `similarity_level: 1` — which passes this plugin's validation, since that only checks the combined set, with the seed-specific resolution left to the server.
  - **A rejected write is fixed.** `audiences_targeting` was documented as `{state: INCLUDE|EXCLUDE, …}`. `state` is `ALL` or `EXISTS`; `INCLUDE` / `EXCLUDE` are the inner `type`. Any targeting write built from that line was rejected.
  - **Two invented parameters removed.** `search_audiences` and `search_lookalike_audiences` were both documented with a `query` parameter. Neither has one.
  - **`search_audiences` has three modes, and the plugin knew one.** It was documented with three parameters out of seven. The by-id mode (`audience_id` + `audience_type`) is the only way to read an audience in full, and `combinable=true` lists a different population for building combined audiences. Both are now documented, in the agent's Tool Reference and the `discovery` skill.
  - **New `knowledge/audiences.md`**, registered in the manifest, carrying the traps that otherwise produce confident wrong answers: `data_type` reports `CUSTOM` for both pixel and combined audiences so it cannot pick `audience_type`; a 404 by id does **not** mean the wrong subtype, because a new audience can stay unreadable by id long after it is created and an archived one stops being readable entirely; and `"Udd with id N doesn't exist"` on a listed id means falling back to the combinable listing.
  - **The capability states are stated once, in a table.** Reads are wired; `create_audience` / `update_audience` are wired too, behind the same preview-then-confirm gate as every other write — an earlier revision of this release held them back, which made the plugin narrower than the surface it wraps for no stated product reason. Building a **predictive audience from a seed** has no tool at any level and stays a UI action, and **no delete endpoint exists anywhere for any audience type**, so archiving — which reverses — is the only retirement.
  - **Round 7 fixes.** Targeting a campaign at an *existing* predictive audience is a normal gated write, but the triage row, the skill's audience section and the capability table all described predictive audiences as read-only or UI-only — so "use a 1% lookalike of my purchasers" could land on a refusal for a write the plugin performs. Named in all three. The similarity wording had been corrected in the canonical file and left wrong in the write-surface row and in the test's own pass criterion. Two more invented parameters turned up in the same resolver table (`search_publishers`' `query` is required, not optional; `search_techno` has no `query` at all). And `scripts/brand-check.sh` scans `knowledge/`, `docs/`, `os/` and the README — widening its pattern does not reach `agents/` or `skills/`, so the two lists still using the retired term there were fixed by hand rather than by the linter.
  - **The two audience writes get their field reference too** (`references/mcp-write-surface.md` §3d): the per-subtype required fields, the different five-field body a customer-list *update* takes, and the traps that make a write look like it worked — a new audience is often unreadable by its own returned id, so a 404 is not a failed create and re-creating is the wrong recovery; `exclude_from_campaigns` on a combined audience reports success and does nothing; the read payload is not a valid update body. The CRM upload gets its own rule: the preview names what is being sent and from where, before the confirmation. W23 covers it.
  - Sites: `knowledge/audiences.md` (new) and `knowledge/manifest.json`, `agents/realize-analyst.md` (Tool Reference + the knowledge-slug list, which drives miss detection and would otherwise send audience questions to the web fallback), `skills/discovery/SKILL.md` (parameters, the id-type split, the returned fields), `skills/manage-campaigns/SKILL.md` (a UI-fallback entry for audiences — there was none, so an archive request had nowhere to land), `skills/manage-campaigns/references/mcp-write-surface.md` and `knowledge/reach-estimation.md` (all three targeting envelopes, not just the one), `knowledge/targeting.md` (it predicted a narrower result set than the tool returns), `README.md` and `docs/realize-best-practices-gap.md` (the capability buckets), `tests/test-scenarios-read.md` (12b read-by-id and the unreadable subtypes), `tests/test-scenarios-write.md` (W22, the "1%" trap) and `.claude/CLAUDE.md` (Open items, and the capability-state rule, which now names three states, with the audience writes now out of the middle one).

### Changed
- **The learning-period guard reads the campaign's reported status instead of counting days.** Learning length varies per campaign — one settles in 5 days, another in 12, another stays volume-starved — so elapsed time never answered the question. `get_campaign` returns the answer directly and the plugin was discarding it: `cvr_learning_status` appeared nowhere outside a phrasing table, and P5 decided on three clock/counter conditions joined by AND.
  - **The old rule could not fire at all on an established campaign.** Condition 1 required the campaign to have been created within the last 7 calendar days, so anything older was treated as mature regardless of its real state — and campaigns commonly report `CVR_LEARNING` for months. A live campaign 69 days old and still learning would have been handed straight to the optimiser for bid changes.
  - **New order of precedence:** `cvr_learning_status` decides (`CVR_LEARNING` / `CVR_LEARNING_LIMITED` fire the guard; `CVR_LEARNING_COMPLETE` clears it; `null` on a Fixed-bid campaign means no learning phase exists; `null` on an approved non-Fixed campaign is treated as still learning, never as done). With a Target CPA set, `target_cpa_learning_status` must additionally read `LEARNING_COMPLETED` — CVR learning completing does not settle a Target CPA. The day heuristic survives only as a last-resort fallback when every field is null, and the answer must then be declared an estimate.
  - **`EMPTY_DISPLAY` is now treated as carrying no information, and is never shown to the user.** Upstream maps two opposite states onto that single label — a campaign that has finished learning and one that has never served. The guardrails table previously translated it as "no Display creatives yet", which is wrong twice over: it is not an ad format, and it appears on mature converting campaigns. Corrected per Performance Oracle's finding on the same field.
  - **Day figures standardised to 7-10 and demoted to an expectation.** The repo carried three different numbers (`7-14`, `7-10`, `~7 days/30 conversions`) because several docs each restated the same fact. They now agree, and they are phrased as what to tell a client to expect, never as the test. Two day figures were deliberately left: the creative-refresh lifespan table in `optimization-flow.md` ("7-14 days" for two verticals) measures creative fatigue, not learning; and Enhanced CPC's longer observed window in `knowledge/bidding.md`, which is now phrased as an observation with a pointer to the status field rather than a rule.
  - Sites: `skills/optimize-campaign/SKILL.md` (P5 rewritten), `knowledge/bidding.md` (held a second full copy of the same broken three-condition guard; now states what the fields mean and defers the gate to the skill), `os/guardrails.md` (translation table), `agents/realize-analyst.md`, `README.md`, `docs/realize-best-practices-gap.md`, `knowledge/custom-rules.md`, `knowledge/site-management.md`, `skills/optimize-campaign/references/optimization-flow.md`, `knowledge/targeting.md` (the `EMPTY_DISPLAY` rewrite).
  - **P5 now has explicit not-applicable cases**, so the guard cannot trap a campaign that will never report a status: Fixed-bid campaigns, non-conversion objectives (awareness, traffic), and campaigns whose **account** has no conversion rules at all skip P5 rather than firing forever. A missing *campaign-level* goal is **not** one of these — per P2 that means the campaign inherits the account default, which is normal, so the guard still fires. An unapproved campaign is routed to an approval explanation instead of being told to wait out a learning phase it is not in. Where P5 is skipped the data-sufficiency gates still apply — "not applicable" is not "mature" — and `site-management` / `custom-rules` keep a volume floor for the no-status case so a day-one Fixed-bid campaign is still protected from publisher blocking and Custom Rules.
  - **The duplicate-campaign exception was dropped.** It said to treat a duplicate as mature after Day 2 even when it reports `CVR_LEARNING` — overruling the authoritative status on an age basis, which is the defect being removed. Nothing in the MCP marks a campaign as a duplicate either, so it rested on the user's word.
  - **P5 gained two exceptions, so a firing guard cannot trap a campaign that is unable to progress.** Holding is right for a campaign moving through learning and wrong for one that is stuck, and a status-driven guard with no exit would leave a low-volume campaign waiting on a condition it can never meet. (A) `CVR_LEARNING_LIMITED` means too little conversion volume — when the daily budget is also under 8× the CPA goal, the budget raise is the remedy and is prescribable, alone and labelled as an intervention during learning. (B) Past roughly 14 days with volume not building, the agent says so and offers the user the choice rather than holding silently; it may not intervene unasked. Both test scenarios accept these and still fail a silent bid change.
  - **Known upstream gap, not fixed here:** the MCP returns the `display_learning_state` column under the name `learning_state`, which is why `EMPTY_DISPLAY` is ambiguous. The underlying `learning_state` column distinguishes `CAMPAIGN_LEARNED` from `CAMPAIGN_NO_EXPOSURE`. Raised with the MCP team; when it is exposed, `EMPTY_DISPLAY` handling can be replaced with a real terminal state.
- **`get_conversion_rules` is paginated and filterable — the "unpaginated, no status filter" guidance is retired.** Upstream added `page` / `page_size` (defaults 1 / 25, max 50, ordered by rule id so pages are stable), a `status` filter (`ACTIVE` / `DISABLED` / `ARCHIVED`), and `search_text` (case-insensitive substring of `display_name` only). The response states the true `total`. The plugin had told the agent none of this existed in 7 places, so on a rule-heavy account it would overflow the tool-result cap and fall into dumped-file recovery where one filtered call now suffices (the field repro — 278 rules / ~270 KB, 102 ACTIVE — is 6 unfiltered pages at `page_size=50`, or 3 filtered to ACTIVE; filtering shrinks the paging rather than removing it).
  - **`status` does not partition the account**, and the docs now say so: `ARCHIVED` selects archived-*and*-disabled rules only, so the three filtered counts need not sum to the unfiltered `total`. Rebuilding "all rules" by concatenating the three statuses is wrong.
  - **The pre-write collision check must not use `status`.** `display_name` is unique across all statuses, so an ACTIVE-only read is not a sound basis for it. `search_text` is still fair game for the name half — status-agnostic and matching `display_name` — provided the returned names are compared **exactly** (it is a contains match) and the search is paged when `total` exceeds a page. The `event_name` half is sound under `status="ACTIVE"`, since the rule is one ACTIVE rule per event; only `ARCHIVED` is lossy. A full unfiltered listing is needed just for ownership reporting. Called out in `manage-campaigns`, its write-surface reference, and `.claude/CLAUDE.md`.
  - The ACTIVE-by-default user listing now has a cheap implementation (`status="ACTIVE"`), with the mandatory skipped-count disclosure unchanged — the count comes from comparing against an unfiltered `total`.
  - Overflow-to-file survives only as a backstop: the first response is now a smaller `page_size`, not a dumped-file recovery.
  - Sites updated: `.claude/CLAUDE.md` (design-decision block rewritten rather than layered, as that block itself instructed), `agents/realize-analyst.md` (tool entry + overflow-to-file paragraph), `skills/discovery/SKILL.md` (capability table + gotchas), `skills/manage-campaigns/SKILL.md`, `skills/manage-campaigns/references/mcp-write-surface.md` (tool row + failure-mode row), `tests/test-scenarios-read.md` (scenario 21 preamble).
- **Reporting is now the metamodel-driven dynamic report; two fixed report tools retired (breaking).** Upstream replaced `get_top_campaign_content_report` and `get_campaign_site_day_breakdown_report` with `get_dynamic_report_settings` + `get_dynamic_report_data` — any combination of the metamodel's dimensions (per the Realize UI's list: campaign, ad, day/week/month/quarter, country, region, DMA, site, platform, browser, OS — the account's live metamodel is authoritative) and metrics, with structured filters, server-side sort, and top-N paging. `get_campaign_history_report` survives, reframed per upstream as the campaign **change/audit log** (not performance data — previously documented here as a performance time-series). The dimensions previously unreachable from the plugin are now covered (country, platform, and OS validated on staging; browser and region per the UI's dimension list).
  - **The two-step workflow is mandatory and documented everywhere the data tool is:** `get_dynamic_report_settings` first — it is the only source of valid fully-qualified column/filter names (account-specific; per-rule conversion metrics vary) — then `get_dynamic_report_data` with names copied verbatim. Dates are `date_preset` XOR `date_from`+`date_to`; `ACCOUNT_ID` and date filters are auto-injected.
  - **The response banner drops the grand `Total`** (now `Records | Grain | pagination`), so the pagination stop-rule changed from "read `Total`" to "page until a short page", and skills state fetched scope instead of implying completeness. `knowledge/reporting-aggregation.md` was rebuilt around this, gaining the sum-vs-ratio / weighted-re-derivation rules the old version lacked, and a preference for server-side aggregation (request the grain you want; don't sum day rows client-side).
  - **Staging-validated 2026-08-20 (10-question comparison, 20/20 runs, raw counters exact):** the behavior quirks found there are recorded as *staging-observed, re-verify at release*: CTR = clicks / **visible** impressions (differs from other surfaces — raw counters reconcile, rates may not), Week buckets start Sunday with labels that can precede the range, `SITE.NAME` 400s (use `SITE.DESCRIPTION`), and entity-attribute dimensions (bidding strategy, Ad CTA) returning unaggregated rows.
  - **`get_campaign_breakdown_report` was NOT retired — it is live and documented as the GROUP / admin-network path.** Upstream disabled it with the other two on 2026-08-24, then restored it on 2026-09-02: the deprecation stranded GROUP and admin-network accounts (the dynamic report 403s on them) and produced a wave of 410s from hard-coded callers. It keeps its legacy banner with a grand `Total`, a flat key/value `filters` object, a `sort_field` limited to `clicks`/`spent`/`impressions`, and server-computed rate columns that must never be recomputed or averaged. The `reports` skill now routes on **account type first** rather than treating the 403 as an error to recover from.

(An MCP event-landing read is the top ask in the adoption plan.)

HAR files carry cookies and session data: Grep-first sliced reading, and no cookies / auth headers / unrelated-domain requests in any output.

  - **The static page check downloads raw HTML (Bash curl of the user's page), not `WebFetch`.** Tested live before shipping: WebFetch converts pages to readable text and strips every `<script>` tag — a page with 11 script tags in raw HTML came back with zero code visible — so a WebFetch-based check would report "no pixel" on every site. The curl ban in `.claude/CLAUDE.md` is scoped to Realize API endpoints and now names this sanctioned exception; Scenario 22A fails a run whose static check went through WebFetch.

- **Overflow survival and ACTIVE-by-default for the unpaginated `get_conversion_rules`.** Found in the field right after the conversion-rule release: the read has no pagination and no status filter, so a rule-heavy account overflows the tool-result cap — observed live at **278 rules / ~270 KB**, of which only **102 were ACTIVE** (~63% of the rules were DISABLED/ARCHIVED — dead weight a caller can't attach to anything). The failure arrives as an overflow error plus a path to a dumped result file, and the one narrowing escape (`rule_id`) is circular — the listing is the only way to learn the IDs.
  - **Recovery is documented everywhere the read is mandated**: read the dumped file in slices and build a slim per-rule projection (`id`, `display_name`, `event_name`, `status`, `advertiser_id`); never re-call unmodified, never abandon, and never treat the overflow as "no rules". The mandatory pre-read before every conversion-rule write inherits the overflow, so the event/name collision and ownership checks now explicitly run against the dumped file — an overflowed pre-read is recovered, never skipped, and never itself a reason to refuse the write (write Scenario W10 gained a matching pass criterion). Collision checks run against **all statuses** — a DISABLED rule still holds its `display_name`.
  - **Listings default to ACTIVE rules with a mandatory one-line disclosure** ("showing N active rules — M disabled/archived skipped, say if you want them"). Non-ACTIVE rules are included only on explicit request; skipping them *silently* is a fail (read Scenario 21, plus a new pass criterion on Scenario 20A).

- **The repo is now its own plugin marketplace** (`.claude-plugin/marketplace.json`, marketplace name `realize`), so `/plugin marketplace add taboola/realize-claude-plugin` followed by `/plugin install realize-plugin@realize` works with no external catalog and no directory approval. Before this, adding the repo as a marketplace failed outright ("Marketplace file not found"), which pushed installs onto ad-hoc hosted catalogs whose cached entries survived the `realize-ads-api` → `realize-plugin` rename — a stale registration kept reporting *"installed realize-ads-api@realize"* on every reinstall (the install identifier comes from the marketplace catalog entry, not from the plugin's own manifest). `INSTALL.md` and `README.md` now carry the working commands plus one-time cleanup steps for machines with a pre-rename registration.

- **Conversion-rule management — the first account-level writes in the plugin.** Upstream shipped `create_conversion_rule`, `update_conversion_rule`, and `get_conversion_rules`; the plugin now wires all three. Tool counts go from 19 read + 6 write to **19 read + 8 write** (`get_conversion_rules` replaces `search_conversion_rules`, so the read count is unchanged). Users can create a conversion rule, change its attribution windows, add or change its revenue value, stop it counting toward Total Conversions, and retire it — all through the existing preview-then-confirm gate with the `▶ WRITE TARGET` header. Per the sync policy in `.claude/CLAUDE.md`, the writes route exclusively through `manage-campaigns` rather than the agent, so the gate cannot be bypassed.
  - **No one-line confirm tier for conversion rules.** Every other write in the plugin scopes to one campaign or one item; a conversion rule feeds attribution and, when `include_in_total_conversions` is set, the account's Total Conversions — which Target CPA and Maximize Conversions bid against. One boolean flip moves reported performance and live bidding across every campaign on the account, so the preview must state that consequence rather than dumping a field diff. Retiring gets the full destructive tier.
  - **The duplicate-event guard is the load-bearing new rule.** Only one ACTIVE rule may hold an event, so a create for a taken event is rejected — and the backend accepts it once the incumbent is DISABLED. That makes "disable the old rule, then retry" look like a legitimate recovery. It is the most damaging move available here: it stops conversion reporting for every campaign using the incumbent. The skill and `os/guardrails.md` both forbid taking it unilaterally; the model surfaces the choice, names the incumbent rule and ID, and waits. Scenario W12 fails the run if a write fires without the user choosing.
  - **Merge semantics are inverted from campaign targeting, and documented as such.** Campaign targeting blocks are full-replace-within-a-section, which trains a read-and-merge reflex. Conversion rules partial-merge *everything*, including `condition` and `effects` — so sending a "complete" object overwrites fields nobody asked to change. Both the skill and the guardrails call this out explicitly because the wrong instinct is the trained one.
  - **The read payload is not a valid update payload.** `get_conversion_rules` returns explicit nulls that fail validation plus seven fields the update tool has no parameter for (`id`, `advertiser_id`, `pixel_id`, `exclude_from_campaigns`, `external_id`, `partner`, `tracked_elements`). Echoing it back is the obvious thing to try, so it's named in the skill, the write-surface reference's failure table, and Scenario W11's pass criteria.
  - **Unit trap documented: `look_back_window` is days (1–30), `view_through_look_back_window` is minutes (1–10080).** "A 7-day view-through window" is `10080`, not `7` — a silent error off by three orders of magnitude. Previews state the unit in the user's terms *and* the stored value; W10 fails on a `7`.
  - Also covered: `type` / `category` / `event_name` immutable after creation (and the READONLY error may name `eventName` even when `type` was what changed, so don't chase the named field); `effects` values are numeric **strings**; `display_name` unique per account and must not contain `^`; there is **no delete tool**; DSP/pixel-based rules can be renamed and retired but their pixel binding stays console-only; and on a parent / NETWORK account the read also returns child accounts' rules, each tagged with its owning `advertiser_id` — check it before writing.
  - **Ownership is not implied by the account you queried, and it runs both directions.** Found while QA-ing against a real account: `get_conversion_rules` on a child account returned 62 rules, **all 62 owned by the parent network** and none by the account queried. The initial note only described the parent→child direction. Both the skill and `discovery` now require reporting ownership rather than presenting results as "this account's rules", and block a write whose `advertiser_id` differs from the `▶ WRITE TARGET` account without explicit confirmation — because a network-attached rule with `include_in_total_conversions=true` moves Total Conversions for every child account under it.
  - **The read surface returns rule kinds the write surface cannot express.** `type: "ENGAGEMENT"` rules, with `condition` properties `SESSION_DEPTH` and `TIME_ON_SITE`, come back from the read; the create/update schemas accept only `BASIC` / `EVENT_BASED` and `URL*` / `EVENT_PARAM_*`. So those rules are readable but not editable here, and resending `type` on one fails schema validation before it reaches the API. Documented so "I can see it, so I can change it" doesn't become a failed write.
  - **Server-side write blocklist documented.** Hit live during QA: the MCP rejects every write on certain accounts by policy, independent of credentials or payload, while reads on the same account keep working. That combination reads exactly like a validation error, so the agent's error handling and the skill's gotchas now say explicitly: don't retry, don't start rewriting fields hunting for the bad one, and report it as an account-level platform restriction.
  - Five write scenarios (W10–W14) with explicit side effects and cleanup, plus read Scenario 20 for the routing ladder. **W10–W14 remain unrun.** Two internal test accounts were tried and every write was rejected; the rejection names the account, but the operative policy (clarified 2026-08-22) is identity-based — **internal Taboola users are excluded from writes**, regardless of account. Running W10–W15 therefore needs a non-internal (client) user, not a different account; probing by attempting writes is not an acceptable search strategy.

- **A tracking routing ladder in `agents/realize-analyst.md`.** Tracking is the highest-traffic topic and the one whose capability line just moved, so it routes explicitly instead of by feel: live rule state → MCP; rule changes → the write gate; method selection and interpretation → `knowledge/tracking.md`; install mechanics the knowledge base doesn't carry → `web-fallback`; nothing available → transparency plus the AM/support redirect. `knowledge/tracking.md` gained a matching section stating what it covers and what it deliberately doesn't, so a reader stops looking there for platform install steps.

If the knowledge base answers the question and a lookup would only add detail, no lookup happens: once web content starts topping up good answers, the curated guidance stops being what users hear and the staleness problem the tiering exists to avoid arrives anyway.
  - **On contradiction the plugin wins, silently.** A help article can lag the platform; the knowledge base reflects current behavior. The web version is discarded and the disagreement is not mentioned — surfacing it would invite the user to go chase the outdated answer.
  - **The source is not named, and URLs are held until asked.** The answer says it came from online sources; it does not say *which* source. `os/guardrails.md` gains a *Carve-out: web-source URLs on explicit request* — the URL is given when the user asks where the answer came from, and never volunteered, because unprompted citations turn every answer into a bibliography and read as low confidence.
  - **Scoped to one domain and one path.** `realize.com/help/` only. A domain allowlist alone is not enough: `/marketing-hub/` is promotional copy on the same host and supplied 3 of 10 results in one live test search and 7 of 10 in another, carrying exactly the guaranteed-outcome framing the guardrails ban and the legacy-category framing `scripts/brand-check.sh` fails on.
  - **Search results are treated as a link index, never as an answer.** The search tool returns the links together with a prose synthesis blended across every hit — including the marketing pages the path filter exists to exclude — so filtering the links does not unread the prose. A correctly domain-restricted live query returned a summary built largely from marketing-page copy that steered the reader toward other documentation. The answer must come from a `/help/` article that was actually fetched.
  - **Taboola's developer documentation is deliberately out of scope.** Its API reference documents the same API the Realize MCP already wraps, and the plugin does not emit endpoint paths, payloads, or client code — so its unique content is content that can't be output. Half its sections (mobile SDK, web integrations, newsroom) are publisher-side, i.e. the wrong audience. Its one advertiser-relevant area, conversion tracking, is already covered at better depth for a non-developer by the help center.
  - **The five gates that can each silently stop a lookup are all closed**: agent `tools`, skill `allowed-tools`, the agent's tool-existence boundary, the harness permission entries (added to `.claude/settings.local.json.example` and documented in `INSTALL.md`), and — least visibly — an affirmative clause in `os/guardrails.md` stating that running the lookup *is* correct behavior. Every other line in that section is restrictive, so the safe reading was previously "never search."
