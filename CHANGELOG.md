# Changelog

All notable changes to this plugin will be documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [SemVer](https://semver.org/).

## [Unreleased]

> **Release gate:** the dynamic-report changes below track an upstream MCP release that is **not yet live on production `mcp.realize.com`**. Do not ship this version until the live tool list shows `get_dynamic_report_settings` / `get_dynamic_report_data` and drops the three retired report tools — then re-verify the staging-observed behaviors marked below against the shipped release.

### Changed
- **Reporting is now the metamodel-driven dynamic report; three fixed report tools retired (breaking).** Upstream replaced `get_top_campaign_content_report`, `get_campaign_breakdown_report`, and `get_campaign_site_day_breakdown_report` with `get_dynamic_report_settings` + `get_dynamic_report_data` — any combination of the metamodel's dimensions (per the Realize UI's list: campaign, ad, day/week/month/quarter, country, region, DMA, site, platform, browser, OS — the account's live metamodel is authoritative) and metrics, with structured filters, server-side sort, and top-N paging. `get_campaign_history_report` survives, reframed per upstream as the campaign **change/audit log** (not performance data — previously documented here as a performance time-series). The dimensions previously unreachable from the plugin are now covered (country, platform, and OS validated on staging; browser and region per the UI's dimension list).
  - **The two-step workflow is mandatory and documented everywhere the data tool is:** `get_dynamic_report_settings` first — it is the only source of valid fully-qualified column/filter names (account-specific; per-rule conversion metrics vary) — then `get_dynamic_report_data` with names copied verbatim. Dates are `date_preset` XOR `date_from`+`date_to`; `ACCOUNT_ID` and date filters are auto-injected.
  - **The response banner drops the grand `Total`** (now `Records | Grain | pagination`), so the pagination stop-rule changed from "read `Total`" to "page until a short page", and skills state fetched scope instead of implying completeness. `knowledge/reporting-aggregation.md` was rebuilt around this, gaining the sum-vs-ratio / weighted-re-derivation rules the old version lacked, and a preference for server-side aggregation (request the grain you want; don't sum day rows client-side).
  - **Staging-validated 2026-08-20 (10-question comparison, 20/20 runs, raw counters exact):** the behavior quirks found there are recorded as *staging-observed, re-verify at release*: CTR = clicks / **visible** impressions (differs from other surfaces — raw counters reconcile, rates may not), Week buckets start Sunday with labels that can precede the range, `SITE.NAME` 400s (use `SITE.DESCRIPTION`), and entity-attribute dimensions (bidding strategy, Ad CTA) returning unaggregated rows.
  - **Reporting account types documented:** PARTNER and NETWORK accounts report; GROUP accounts and admin networks return 403 by design — pick another account, don't retry or re-auth.
  - **Every stale claim site updated in the same change** (per the stale-capability-claims policy): the agent's Tool Reference, examples, claim-validation list, CSV/sort/filter technical specs, and tool-existence boundary (now naming the three retired tools as off-surface); the `reports` skill and both its references; `optimize-campaign`'s dimension table; `campaigns`' top-campaign flow; `knowledge/reporting-aggregation.md`; `CLAUDE.md`'s diagram, CSV section, and a new design-decision note; `README.md`'s skills table; and read Scenarios 5–9. `tests/test-scenarios-dynamic-report.md` (the 10 prepared comparison questions) and `docs/reports-gaps.md` (with a migration status update) are committed alongside.

### Added
- **`diagnose-tracking` skill — pixel-health diagnosis, previously an explicit refusal.** Adapted from an internal Taboola support team's pixel-diagnostics skill with everything internal stripped — no internal databases, no Salesforce intake, no internal config flags; adoption notes and the MCP capability asks are in `docs/2026-08-22-pixel-expert-adoption-plan.md`. The skill verifies the Taboola Pixel end to end from evidence a client can produce: it fetches the user's page (static install check), reads a user-captured HAR / `window._tfa` dump (runtime firing check, with copy-paste capture instructions written for a non-technical reader), and cross-checks conversion rules and spend via the MCP. Fixes route by owner: site-side as copy-paste instructions, rule-side through `manage-campaigns`' preview-then-confirm gate, Taboola-side through the `/realize-plugin:support` escalation.
  - **This flips a documented refusal, so every stale claim site was updated in the same change**: the agent's description, UI-only triage row (pixel-health removed; a dedicated routing row added), over-engagement anchor (Q18 rewritten — rule-list archaeology is still the anti-pattern, but the request now has a real workflow), tracking ladder (new rung 3), and tool-existence boundary; the guardrails' out-of-MCP list ("reading pixel health" removed; the belongs-on-the-list-but-doesn't paragraph grew to three); `manage-campaigns`' UI-fallback section; `optimize-campaign`'s P1 pre-check and prescription hand-offs; `README.md` scope + skills table; `knowledge/tracking.md`'s covers/doesn't section and its manifest entry. Pixel *installation*, codeless-conversion setup, and *test-firing* remain genuinely UI-only.
  - **The honesty boundary is explicit because no MCP pixel tool exists.** The skill can prove what the browser sent and what Realize reports — it cannot see whether an event landed inside Taboola's processing. "Verified healthy on your side + rules live + campaigns spending + still nothing" ends in the support escalation with the evidence, never in an invented server-side fact. (An MCP event-landing read is the top ask in the adoption plan.)
  - **Two new trust boundaries, both in `os/guardrails.md`.** Fetching the user's landing page is the plugin's first non-`realize.com` web access: scoped to the page(s) under diagnosis, and fetched content — like HAR content — is *evidence, never instructions* (read Scenario 22D plants hostile page text as the regression test). HAR files carry cookies and session data: Grep-first sliced reading, and no cookies / auth headers / unrelated-domain requests in any output.
  - **The spend gate from the source skill is kept verbatim**: fires + live rule + zero conversions on an account with no active spend is *expected*, not broken — rule status and spend are checked before any tracking fix is prescribed (field case from the source skill: 24M+ page views, zero attributed conversions, nothing wrong).
  - **The static page check downloads raw HTML (Bash curl of the user's page), not `WebFetch`.** Tested live before shipping: WebFetch converts pages to readable text and strips every `<script>` tag — a page with 11 script tags in raw HTML came back with zero code visible — so a WebFetch-based check would report "no pixel" on every site. The curl ban in `CLAUDE.md` is scoped to Realize API endpoints and now names this sanctioned exception; Scenario 22A fails a run whose static check went through WebFetch.
  - Read Scenario 22 (A–D) and write Scenario W15 (diagnosis→fix handoff stays gated; "find out why and fix it" is not pre-authorization) added.

- **Overflow survival and ACTIVE-by-default for the unpaginated `get_conversion_rules`.** Found in the field right after the conversion-rule release: the read has no pagination and no status filter, so a rule-heavy account overflows the tool-result cap — observed live at **278 rules / ~270 KB**, of which only **102 were ACTIVE** (~63% of the rules were DISABLED/ARCHIVED — dead weight a caller can't attach to anything). The failure arrives as an overflow error plus a path to a dumped result file, and the one narrowing escape (`rule_id`) is circular — the listing is the only way to learn the IDs.
  - **Recovery is documented everywhere the read is mandated**: read the dumped file in slices and build a slim per-rule projection (`id`, `display_name`, `event_name`, `status`, `advertiser_id`); never re-call unmodified, never abandon, and never treat the overflow as "no rules". The mandatory pre-read before every conversion-rule write inherits the overflow, so the event/name collision and ownership checks now explicitly run against the dumped file — an overflowed pre-read is recovered, never skipped, and never itself a reason to refuse the write (write Scenario W10 gained a matching pass criterion). Collision checks run against **all statuses** — a DISABLED rule still holds its `display_name`.
  - **Listings default to ACTIVE rules with a mandatory one-line disclosure** ("showing N active rules — M disabled/archived skipped, say if you want them"). Non-ACTIVE rules are included only on explicit request; skipping them *silently* is a fail (read Scenario 21, plus a new pass criterion on Scenario 20A).
  - **Interim guidance**: upstream has a fix planned for pagination/status filtering on this endpoint. When it ships, this guidance is stale-capability-claims class — grep for "overflow" and "no status filter" and rewrite.

- **The repo is now its own plugin marketplace** (`.claude-plugin/marketplace.json`, marketplace name `realize`), so `/plugin marketplace add taboola/realize-claude-plugin` followed by `/plugin install realize-plugin@realize` works with no external catalog and no directory approval. Before this, adding the repo as a marketplace failed outright ("Marketplace file not found"), which pushed installs onto ad-hoc hosted catalogs whose cached entries survived the `realize-ads-api` → `realize-plugin` rename — a stale registration kept reporting *"installed realize-ads-api@realize"* on every reinstall (the install identifier comes from the marketplace catalog entry, not from the plugin's own manifest). `INSTALL.md` and `README.md` now carry the working commands plus one-time cleanup steps for machines with a pre-rename registration.

- **Conversion-rule management — the first account-level writes in the plugin.** Upstream shipped `create_conversion_rule`, `update_conversion_rule`, and `get_conversion_rules`; the plugin now wires all three. Tool counts go from 19 read + 6 write to **19 read + 8 write** (`get_conversion_rules` replaces `search_conversion_rules`, so the read count is unchanged). Users can create a conversion rule, change its attribution windows, add or change its revenue value, stop it counting toward Total Conversions, and retire it — all through the existing preview-then-confirm gate with the `▶ WRITE TARGET` header. Per the sync policy in `CLAUDE.md`, the writes route exclusively through `manage-campaigns` rather than the agent, so the gate cannot be bypassed.
  - **No one-line confirm tier for conversion rules.** Every other write in the plugin scopes to one campaign or one item; a conversion rule feeds attribution and, when `include_in_total_conversions` is set, the account's Total Conversions — which Target CPA and Maximize Conversions bid against. One boolean flip moves reported performance and live bidding across every campaign on the account, so the preview must state that consequence rather than dumping a field diff. Retiring gets the full destructive tier.
  - **The duplicate-event guard is the load-bearing new rule.** Only one ACTIVE rule may hold an event, so a create for a taken event is rejected — and the backend accepts it once the incumbent is DISABLED. That makes "disable the old rule, then retry" look like a legitimate recovery. It is the most damaging move available here: it stops conversion reporting for every campaign using the incumbent. The skill and `os/guardrails.md` both forbid taking it unilaterally; the model surfaces the choice, names the incumbent rule and ID, and waits. Scenario W12 fails the run if a write fires without the user choosing.
  - **Merge semantics are inverted from campaign targeting, and documented as such.** Campaign targeting blocks are full-replace-within-a-section, which trains a read-and-merge reflex. Conversion rules partial-merge *everything*, including `condition` and `effects` — so sending a "complete" object overwrites fields nobody asked to change. Both the skill and the guardrails call this out explicitly because the wrong instinct is the trained one.
  - **The read payload is not a valid update payload.** `get_conversion_rules` returns explicit nulls that fail validation plus seven fields the update tool has no parameter for (`id`, `advertiser_id`, `pixel_id`, `exclude_from_campaigns`, `external_id`, `partner`, `tracked_elements`). Echoing it back is the obvious thing to try, so it's named in the skill, the write-surface reference's failure table, and Scenario W11's pass criteria.
  - **Unit trap documented: `look_back_window` is days (1–30), `view_through_look_back_window` is minutes (1–10080).** "A 7-day view-through window" is `10080`, not `7` — a silent error off by three orders of magnitude. Previews state the unit in the user's terms *and* the stored value; W10 fails on a `7`.
  - Also covered: `type` / `category` / `event_name` immutable after creation (and the READONLY error may name `eventName` even when `type` was what changed, so don't chase the named field); `effects` values are numeric **strings**; `display_name` unique per account and must not contain `^`; there is **no delete tool**; DSP/pixel-based rules can be renamed and retired but their pixel binding stays console-only; and on a parent / NETWORK account the read also returns child accounts' rules, each tagged with its owning `advertiser_id` — check it before writing.
  - **Ownership is not implied by the account you queried, and it runs both directions.** Found while QA-ing against a real account: `get_conversion_rules` on a child account returned 62 rules, **all 62 owned by the parent network** and none by the account queried. The initial note only described the parent→child direction. Both the skill and `discovery` now require reporting ownership rather than presenting results as "this account's rules", and block a write whose `advertiser_id` differs from the `▶ WRITE TARGET` account without explicit confirmation — because a network-attached rule with `include_in_total_conversions=true` moves Total Conversions for every child account under it.
  - **The read surface returns rule kinds the write surface cannot express.** `type: "ENGAGEMENT"` rules, with `condition` properties `SESSION_DEPTH` and `TIME_ON_SITE`, come back from the read; the create/update schemas accept only `BASIC` / `EVENT_BASED` and `URL*` / `EVENT_PARAM_*`. So those rules are readable but not editable here, and resending `type` on one fails schema validation before it reaches the API. Documented so "I can see it, so I can change it" doesn't become a failed write.
  - **Server-side write blocklist documented.** Hit live during QA: the MCP rejects every write on certain accounts by policy, independent of credentials or payload, while reads on the same account keep working. That combination reads exactly like a validation error, so the agent's error handling and the skill's gotchas now say explicitly: don't retry, don't start rewriting fields hunting for the bad one, and report it as an account-level platform restriction.
  - Five write scenarios (W10–W14) with explicit side effects and cleanup, plus read Scenario 20 for the routing ladder. **W10–W14 remain unrun.** Two internal test accounts were tried and every write was rejected; the rejection names the account, but the operative policy (clarified 2026-08-22) is identity-based — **internal Taboola users are excluded from writes**, regardless of account. Running W10–W15 therefore needs a non-internal (client) user, not a different account; probing by attempting writes is not an acceptable search strategy.

- **A tracking routing ladder in `agents/realize-analyst.md`.** Tracking is the highest-traffic topic and the one whose capability line just moved, so it routes explicitly instead of by feel: live rule state → MCP; rule changes → the write gate; method selection and interpretation → `knowledge/tracking.md`; install mechanics the knowledge base doesn't carry → `web-fallback`; nothing available → transparency plus the AM/support redirect. `knowledge/tracking.md` gained a matching section stating what it covers and what it deliberately doesn't, so a reader stops looking there for platform install steps.

### Added
- **`web-fallback` skill — public-documentation fallback for questions the knowledge base doesn't cover.** The knowledge base is 12 topic files; an advertiser can ask hundreds of reasonable "how do I…" questions that land just outside them. Those previously got a thin answer from model priors or a shrug, and the first is worse than the second. Closes the help-center connection gap identified as top-priority in an internal capability review. The skill searches Taboola's public advertiser help documentation and answers with a *"here's what I found online"* framing.
  - **A fallback, never a supplement.** It fires only on a real miss, and the miss is judged **per question, not per topic** — `knowledge/tracking.md` covers pixel-vs-S2S selection and validation, so *"which tracking method should I use?"* never reaches a lookup, while *"how do I install the pixel on Shopify?"* does. If the knowledge base answers the question and a lookup would only add detail, no lookup happens: once web content starts topping up good answers, the curated guidance stops being what users hear and the staleness problem the tiering exists to avoid arrives anyway.
  - **On contradiction the plugin wins, silently.** A help article can lag the platform; the knowledge base reflects current behavior. The web version is discarded and the disagreement is not mentioned — surfacing it would invite the user to go chase the outdated answer.
  - **The source is not named, and URLs are held until asked.** The answer says it came from online sources; it does not say *which* source. `os/guardrails.md` gains a *Carve-out: web-source URLs on explicit request* — the URL is given when the user asks where the answer came from, and never volunteered, because unprompted citations turn every answer into a bibliography and read as low confidence.
  - **Scoped to one domain and one path.** `realize.com/help/` only. A domain allowlist alone is not enough: `/marketing-hub/` is promotional copy on the same host and supplied 3 of 10 results in one live test search and 7 of 10 in another, carrying exactly the guaranteed-outcome framing the guardrails ban and the legacy-category framing `scripts/brand-check.sh` fails on.
  - **Search results are treated as a link index, never as an answer.** The search tool returns the links together with a prose synthesis blended across every hit — including the marketing pages the path filter exists to exclude — so filtering the links does not unread the prose. A correctly domain-restricted live query returned a summary built largely from marketing-page copy that steered the reader toward other documentation. The answer must come from a `/help/` article that was actually fetched.
  - **Taboola's developer documentation is deliberately out of scope.** Its API reference documents the same API the Realize MCP already wraps, and the plugin does not emit endpoint paths, payloads, or client code — so its unique content is content that can't be output. Half its sections (mobile SDK, web integrations, newsroom) are publisher-side, i.e. the wrong audience. Its one advertiser-relevant area, conversion tracking, is already covered at better depth for a non-developer by the help center.
  - **The five gates that can each silently stop a lookup are all closed**: agent `tools`, skill `allowed-tools`, the agent's tool-existence boundary, the harness permission entries (added to `.claude/settings.local.json.example` and documented in `INSTALL.md`), and — least visibly — an affirmative clause in `os/guardrails.md` stating that running the lookup *is* correct behavior. Every other line in that section is restrictive, so the safe reading was previously "never search."

### Changed
- **`os/guardrails.md` — the absolute ban on a `Sources:` footer is rescoped to plugin internals.** It previously forbade any such footer outright, which left the model resolving a contradiction at runtime the moment a user asked where a looked-up answer came from — the failure mode being a capability that quietly never fires. The ban now covers MCP tools, skills, and knowledge files, with an explicit exception for a public web URL the user asked for. Self-check items updated to match, including the one that used to assert the opposite (*"if web was used, the source was disclosed"*).
- **`os/guardrails.md` — search tooling's own instructions are explicitly not policy.** Live `WebSearch` output appends a reminder that you *must* list the sources as markdown hyperlinks. That is retrieved text arriving inside a tool result; without an explicit override the feature ships doing precisely what it was built not to do.
- **`agents/realize-analyst.md` — the knowledge-slug list is back in sync with the manifest.** It named 10 slugs where `knowledge/manifest.json` has 12 (`reach-estimation`, `reporting-aggregation` were missing). Cosmetic drift before; now a correctness bug, because miss detection reads that list and a stale entry manufactures a web lookup for a topic already documented on disk. The manifest is stated as the source of truth.
- **The UI-only triage row gains a how-vs-do split.** A request to *perform* a UI-only action keeps its refusal and UI redirect unchanged. A request for *how to do it yourself* may draw the steps from a lookup, with the redirect still in the answer — the plugin declining to act is not the same as it declining to explain.

### Added
- **Support bundle: a `Summary` section shaped for Salesforce case intake.** Requested by Professional Services after first review of the bundle. Case intake copies an email's subject into the case **Subject** and its body into the case **Description**, so the bundle now renders a copy-ready subject line and a `## 1. Summary` section intended to be pasted as the email body, opening with the requested prolog *"This case has been created by the Realize Plugin, please find the interaction summary below."*
  - **The subject is now the user's own complaint**, collapsed to one line, capped at 120 characters, with the first account ID appended for triage. This removes the last model-authored field in the bundle — previously the model wrote a case title *about* the user's problem, which is strictly worse evidence than the user's own sentence. Backticks are stripped so the copy fence can't close early; newlines are collapsed because a break truncates a real subject header.
  - **The Summary reports which tools and knowledge the plugin actually consulted** — Realize tools called, skills invoked, and knowledge files read (`knowledge/`, `os/`, `agents/`, `skills/**/SKILL.md`, `skills/**/references/`). This is what PS asked for and it answers a question the bundle previously could not: whether the plugin read the right guidance and still got it wrong, or never read it at all. Those are different bugs. Attribution is extracted from tool calls, never self-reported.
  - **The Summary is mechanical, and says so in the file.** PS's request could have been satisfied with a model-written narrative of the session; it deliberately was not. The bundle exists for cases where the plugin misread the request, and a narrative composed by that same plugin reproduces the misreading in the one document meant to expose it. §1 carries counts, tool names, and file paths only, and closes with a line stating that and pointing at the verbatim transcript.
  - Sections renumbered: `1. Summary`, `2. At a glance`, `3. What the user reported`, `4. Failed actions`, `5. Realize actions attempted`, `6. Full transcript`. `--title-file` is now the fallback for a run with no user description rather than the normal path.
  - **The complaint is now redacted before it becomes the subject.** It stays the user's own wording — `redact()` only removes credential-shaped values, and its flat rule is `=`-only with a length floor so prose is untouched — but users paste error output they never read, and that text now travels into an email subject line. Applies to Section 3 as well.
  - **Subject truncation no longer deletes the complaint.** `account_id` is an opaque API string with no length bound; with a long one, `slice(0, MAX - suffix.length - 1)` went negative and sliced from the *end*, replacing the user's entire sentence with a bare `…` in the subject describing their own problem. A `MIN_SUBJECT_TEXT_CHARS` floor now drops the account suffix instead — Section 2 still lists every account acted on.
  - **`knowledgeRef` is anchored to the plugin root.** Unanchored, a user's own `~/Documents/os/notes.md` was reported as plugin guidance. A false entry is worse than none here: the section exists to tell "read the right guidance and still got it wrong" from "never read it", and a wrong entry answers that question incorrectly.
  - A recorded `Skill` call is no longer also counted under "Other tools used", where it double-reported the same invocation.
  - Test suite grows from 36 to **77 assertions** covering subject derivation (including that `$12.40` survives, that a pasted `Bearer` token does not, and that "Secret: Summer Sale" prose is not shredded), the over-long `account_id` regression, `knowledgeRef` root anchoring and its deliberate exclusions, skill/knowledge attribution through `analyze`, and a structural check that the rendered Summary contains no free prose line at all — asserted by line shape rather than a keyword blacklist, so a future edit can't slip a narrative past it with different phrasing.

- **`support` skill — user-driven support escalation, invoked as `/realize-plugin:support`.** Users run the plugin in their own terminal, so Taboola Professional Services has no visibility into these conversations; a "the plugin gave me the wrong number" report previously arrived with no evidence attached. The command packages the session into a single Markdown file the user emails to `Support@taboola.com`. Contents: a suggested case title, an at-a-glance diagnostic table (session ID, timestamps, turn counts, accounts/campaigns/items involved, actions attempted, **failed count**, plugin + Claude Code version, platform), the user's complaint verbatim, every failed Realize action with its parameters and error text, an ordered table of all actions attempted, and the full rendered transcript. Everything above the transcript is mechanically extracted by `skills/support/scripts/build-bundle.js` — deliberately never model-authored, so a plugin that misread the user can't carry that misreading into its own bug report.
  - **Local-only by design.** The script writes one file (Desktop → Downloads → home) and prints the path. There is no upload path; transmitting is the user's decision.
  - **Preview-then-confirm**, mirroring the `manage-campaigns` write gate: `--preview` reports what would be captured (including size and the account IDs involved) and writes nothing until the user confirms.
  - **Redaction**: bearer tokens, `access_token` / `refresh_token` / `id_token`, `api_key`, `password`, `client_secret`, and JWTs are stripped — in both JSON (`"password": "…"`) and flat (`password=…`) form, since the actions table renders tool inputs as `key=value` where a JSON-shaped pattern never fires. Redaction runs *before* any length-shortening, so a credential can't be cut below the length the patterns match on. `account_id`, `campaign_id`, and `item_id` are deliberately **preserved** — PS cannot reproduce an issue without them.
  - **User text is passed by file (`--complaint-file` / `--title-file`), never as a shell argument.** Under a quoted shell argument the complaint is rewritten before it is ever read: `$12.40` arrives as `2.40`, `$500` as `00`, and backticks or `$(…)` execute. Currency is ubiquitous in this domain and users paste error text they didn't author, so the evidence has to bypass the shell entirely.
  - **Counts reflect the conversation, not the log.** The transcript stores tool results as `user` records and splits one reply across many `assistant` records, so naive counting overstated a 7-message exchange as 63 user turns and 51 replies. User messages now require a text block; replies key off `stop_reason: "end_turn"`; tool results are reported on their own line.
  - **Failure is legible.** `main()` is wrapped so a write error yields a plain-language message and exit 1 rather than a Node stack trace exposing internal paths — the audience is a non-technical user already having a bad day.
  - **Cloud-sync aware.** Desktop is preferred for findability, but an enterprise OneDrive-redirected Desktop would silently upload customer campaign data on write, contradicting the local-only guarantee. Synced folders are skipped, and the preview warns if only synced destinations exist.
  - **Redaction is structural where the key is known.** The actions table matches on the parameter *name* rather than pattern-matching rendered text. An earlier regex-only approach that matched `secret:` / `authorization:` in prose shredded legitimate ad copy — "Secret: Summer Sale" became "Secret: `<redacted>` Sale" — which is the opposite of what an evidence bundle is for. The remaining flat-text rule is `=`-only with a length floor; the JSON rule covers the colon form.
  - **Table cells collapse whitespace.** A newline inside any tool-input value (creative titles and descriptions routinely have them) previously ended the Markdown row early and corrupted every row below it.
  - **Fails loudly, never falsely.** An unreadable `--complaint-file` / `--title-file` exits 1 without writing, rather than emitting a bundle that tells support *"The user did not add a description"* about a user who did. `--out` refuses to overwrite an existing file without `--force`. Transcripts above 256 MB are refused with an explanation instead of an out-of-memory crash.
  - Truncation closes any code fence or `<details>` block the cut left open. Multi-line titles are collapsed so the case's subject line survives.
  - **Refuses to write inside a git working tree.** The bundle holds customer campaign data and this repo is public, so a bundle written into it is one `git add -A` from publication. SKILL.md already said not to, but an instruction to the model is not a control — this is enforced in the script, with `--allow-git` as a deliberate escape hatch. The default destination now also skips git work trees (a dotfiles-managed home directory is one) and falls back to the OS temp directory.
  - **Object-valued parameters are serialized in the actions table** instead of flattening to `[object Object]` via `String()`. Realize targeting blocks are objects, so the previous rendering told PS nothing about exactly the payloads whose failures are hardest to diagnose.
  - **Path comparison is separator-normalized.** `path.join` yields backslashes while a hand-written `--out` usually has forward slashes; a raw compare meant the OneDrive warning silently failed to fire on precisely the folder it exists to catch.
  - Auto-generated filenames that collide (two runs in the same second) get a numeric suffix rather than erroring; an explicit `--out` collision still refuses without `--force`. Header rows relabelled "acted on" — the IDs come from request parameters, so a session that only browsed results correctly shows none.
  - **Truncation is tiered by how diagnostic the output is.** Realize responses get 20,000 characters; other tool output stays at 2,000. A report CSV usually *is* the case — "the CPA here disagrees with the UI" is answered by the rows behind the number — and under the previous uniform cap only ~13 of 250 rows survived, so the disputed row was typically the one missing. Bulk output from unrelated tools stays capped so the bundle remains email-attachable.
  - **The git refusal no longer names its own override.** `--allow-git` still exists for maintainers but appears in neither the error message nor `SKILL.md`: the model that hits the error reads that message as its next instruction, and the correct next step is a different path, not a bypass on the one control between customer data and a public repo. Documented in `CLAUDE.md` only.
  - The skill now deletes the scratch `complaint.txt` / `title.txt` after writing the bundle.
  - **Shipped as one skill, not a command plus a skill.** An earlier split (`commands/support.md` routing into a `support-bundle` skill) registered *both* as invocable, so users saw two near-identical entries — `/realize-plugin:support` and `/realize-plugin:support-bundle` — with no way to tell which was correct. The thin command added nothing the skill could not do, so it was removed and the skill renamed to `support`. One feature, one entry. Caught during first live testing.
  - **Invocation is `/realize-plugin:support`, not `/support`.** Plugin components are namespaced by plugin name. Every doc, the guardrails escalation footer users actually see, and the test scenarios said the bare form, which fails with `Unknown command`. Corrected across `README.md`, `INSTALL.md`, `os/guardrails.md`, the skill, and the scenarios. Caught during first live testing.
